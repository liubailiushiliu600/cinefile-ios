## 1. 播放进度记忆（新增 `Player/PlaybackProgressStore.swift`）

- 键 = `entry.id + "|" + size`。带上 size，换片源（同名片、不同编码）不会继承旧进度。
- 存 `Application Support/Cinefile/progress.json`，结构 `{v, items:{key:{position,duration,updatedAt,finished}}}`。
- 写入节流：内存先更新，磁盘最多每 8 秒落一次；播放页退出 / 切后台（`scenePhase != .active`）强制落盘。
- 修剪：最多 400 条，按 `updatedAt` 保留最近的。
- 规则：
  - `position < 5s` 且未看完 → **删除**记录（避免「看 3 秒」污染徽章）；
  - `finished = duration - position <= 15s`，或进度 ≥ 95% → 显示「已看」；
  - 剩余不足 30 秒不续播（那是片尾字幕），只显示进度。

UI：
- `VideoCard` 右下角徽章从写死的「未看」变成「未看 / 看 62% / 已看」，配色用现成的
  `CF.stateUnwatched` / `stateWatching` / `stateWatched`；
- 卡片缩略图底部加 3pt 琥珀进度条（仅 1%–99% 显示）；
- 因为进度是播放器写的，卡片在 `onAppear` 里重读一次，从播放页返回即刷新。

播放器：
- `PlayerScreen(url:title:progressKey:)`，`progressKey` 为空则不记忆（旧 SMBBrowserView 路径仍可用）。
- 续播用 `:start-time=<秒>` 作为 media option（demux 阶段就 seek，不是先解码再跳）。
- 续播时顶部弹一条「已从 12:34 继续播放」+「从头播放」按钮，6 秒自动消失。

## 2. 播放器手势（`PlayerScreen`）

- 手势层是 ZStack 里**视频之上、控制条之下**的一层透明视图（`Color.clear + contentShape`），
  所以进度条 Slider 和按钮永远优先，不会被手势抢走；
- 横向拖动 = 快进/快退，整屏宽度扫过的时长 = `clamp(duration*0.6, 90s, 600s)`，
  松手才真正 seek（拖动过程中只更新 HUD 和进度条预览）；
- 左半屏竖向拖动 = 屏幕亮度（`UIWindowScene.screen.brightness`，不用已废弃的 `UIScreen.main`）；
- 右半屏竖向拖动 = 播放器音量（0–200，与 VLC 一致）；
- HUD 是居中胶囊：`01:23:45 / 02:00:00` / `音量 65%` / `亮度 40%`；
- 单击仍然只是切控制条显隐。

## 3. 启动自动重连（`PeerStore` + `AppState`）

- `PeerStore` 新增 `lastNetworkPeerId` / `lastNetworkFolder` / `preferNetworkOnLaunch`
  （UserDefaults，键前缀 `cinefile.`）。
- 打开本地片库 / 关闭片库时把 `preferNetworkOnLaunch` 置 false；成功连上网络库时置 true 并清空路径。
- 启动时：偏好网络 → 取回 peer + Keychain 凭据 → **先做一次 445 端口 TCP 探测**（1.8s 超时，
  `NWConnection`，`SMBClient.isReachable`）→ 通才连 SMB。PC 关机/不在同一 Wi-Fi 时直接回退到
  最近的本地片库，不弹错误框（原方案会卡几十秒）。
- 连上后回跳到上次所在子目录。

顺带：`access(for: peer)` 的 IPv4 替换逻辑从 `PeerService` 下沉到 `PeerStore`，
这样 `AppState` 不依赖 `PeerService` 也能拿到可用凭据。

## 4. 网络缩略图（`RemoteThumbnailService` 重写调度部分）

四条改动，都是「不改协议、不加 PC 端依赖」的：

1. **双队列**：`priorityQueue`（当前屏幕上的卡片，有 continuation 在等）优先于
   `backgroundQueue`（预取）。VLC 同一时刻仍只跑 1 个实例（3 GB 内存红线，不要调回 2）。
2. **去掉固定 0.5 秒等待**：旧实现 `saveVideoSnapshot` 之后无条件等 0.5s 再读文件。
   现在每 60–70ms 轮询目标 jpg（>512 字节即成功），最多 8 次（≈560ms）。正常情况省 300–400ms/张。
3. **目录级预取**：`AppState` 每次列完目录调用 `RemoteThumbnailService.prefetch(...)`，
   把还没缓存的文件按目录顺序入后台队列，上限 48 个/目录（跳过多于 48 个的部分，
   下次进目录继续）。播放开始 `pauseForPlayback()` 会把在跑的 job 放回各自队列头部，
   预取不会和正在看的片子抢带宽；预取 job 没有等待者，失败静默。
4. **缓存键加 mtime**：`entry.id|size|mtime|remote-thumb-v2`。旧键只有 id+size，
   同名同大小换片源会命中旧图。

预期效果：首次进目录仍是 ~1–1.5s/张（网络 + VLC 解封装的下限），但**可见的 6–9 张**先出，
剩下的在后台补完；同一目录第二次进入 0 成本。

### 为什么没做「PC 端预生成缩略图」（交接文档 §8.1 方案 A）

查过本机实况后放弃，理由写在这里免得下次重走：

- PC 端缩略图在 `<安装目录>/data/cache/thumbs/<sha1>.jpg`，**不在 SMB 共享目录里**，
  共享出去的是用户选的媒体文件夹（这里 `D:\新建文件夹`，86 个视频 / 473 张缓存）。
- 缓存键 = `sha1(f"{path}|{mtime:.6f}|{size}|thumb-v2")`，其中 `path` 是 Windows 绝对路径。
  用本机文件反算命中率 **0/86**（试过盘符路径/UNC 路径、正反斜杠、几种 mtime 格式），
  说明 PC 端写缓存时用的 `Entry.path` 形态与离线推导不一致，而 iOS 侧既拿不到共享根目录的
  绝对路径、也没有协议字段能取。
- PC 端**没有 ffmpeg，也没有 mpv.exe**（`_internal` 里没有，`bin/` 不存在），
  所以「让 PC 侧脚本重新生成缩略图」这条路在本机不具备条件。

结论：要么改 PC 端（发布缩略图索引到共享里），要么维持现状。前者需要 PC 端源码改动 +
用户手动跑一次脚本，本轮不做。
